# SGI Onyx 3000 (IP35)

The Onyx 3000 is the [Origin 3200](origin3200-ip35.md) with a graphics brick.
Select `machine.profile = "onyx3000_ip35"` and the graphics brick with
`[graphics] board`. The board decides the composition:

| `[graphics] board` | Composition |
|---|---|
| `ir3` (the default) | One C-brick, the I-brick and one single-pipe G-brick: an Onyx 3200. The InfiniteReality3 pipe is at widget 11 of the I-brick's XBridge. |
| `v12` | Two C-bricks joined by the NUMAlink cable. The first has the I-brick. The second has a V-brick on its own XIO connector: an XBridge with a VPro V12 at widget 8. |

`none` is refused: an Onyx 3000 without graphics is the Origin 3200. `ir2` and
`ir2e` are refused with the pipe table's reason, which lists where each product
shipped; the Onyx 3000 takes `ir3`. The shared keys, `[onyx3000]` (the keys of
`[origin3200]` except `c_bricks`, which the board fixes) and
`[fibre_channel.disk.N]` apply as on the Origin 3200; see its guide for the C-brick, the I-brick, the Fibre Channel
adapter and the console.

```toml
[machine]
profile = "onyx3000_ip35"
cpu = "r12000"

[graphics]
board = "ir3"           # or "v12"

[fibre_channel.disk.1]
path = "system.raw"
overlay = true
```

## The G-brick

The pipe is the InfiniteReality KONA widget, the same board the Onyx2 fits
(`src/dev/kona`). Its DMA is the chip's inbound traffic for widget 11, and its
interrupt packets go to the address the driver programs into the pipe, which
Bedrock reads as the processor interface. The Onyx2's Hub ignores that address;
the pipe hands it over with each packet, and the widget it sends from.

Established: each InfiniteReality pipe sits at widget 11 of an I-brick or
X-brick XBridge, over a direct cable with no router, and each pipe has its own
C-brick. The smallest real configuration is one C-brick, one I-brick and one
single-pipe G-brick.

PROM 6.210 reaches the System Maintenance Menu, lists `KONA Graphics Board` in
`hinv`, and IRIX 6.5 boots to a login and lists `Graphics board:
InfiniteReality3`, with the GE16-4 board at `xtalk/11` of the I-brick's module.

## The V-brick

The V-brick is an XBridge on the second C-brick's Bedrock with the V12 at
widget 8. DMA and interrupt packets reach the chip as any widget's do, as on
the Fuel and the Tezro. PROM 6.210 lists `ODYSSEY Graphics Board` in module
001c07 under an `XBRICK Bridge`, and IRIX boots to a login on both nodes with
the V12 at `xtalk/8`.

Established: the V-brick holds an XBridge and cables to a C-brick of its own.
Inferred: it has no PCI devices.

## Approximations and limits

Each of these is a choice or an inference, not a hardware fact.

- **The V12's widget is 8.** 8 and 12 are equal candidates, from the X-brick's
  slot table if the V-brick's midplane matches it. 8 is the model's choice; no
  V-brick widget listing is captured.
- **The V-brick's controller answers as an X-brick.** The L1 firmware names no
  V-brick, and a V-brick runs the X-brick's personality, so the controller
  answers the type letter `X` and the PROM prints `XBRICK`. The V-brick's own
  controller is a stub like the I-brick's: it answers the identity and the
  attached-brick list and serves every other request as its C-brick's. Which
  board records a V-brick's controller answers with is not established; the
  X-brick's are an inferred candidate. Its rack bay (11) is a choice.
- **The V-brick's XBridge has both PCI heads, empty,** as the chip always does.
- **The G-brick's own controller and its cable are not modelled.** The pipe is a
  widget of the I-brick's XBridge. A pipe behind an N-brick is not modelled.
- **The I-brick's controller lists the G-brick** at port 2 of its attached-brick
  reply (request `0xc`), letter `G`, at rack bay 24. The PROM asks for that list
  when the I-brick's second port is up: with no name for the brick there it
  takes the port for a second host C-brick and finds no BaseIO. The port, the
  letter and the bay are the model's choice; no real reply is captured.
- **One pipe, one raster manager,** and InfiniteReality3 only on the G-brick.
- **The graphics console needs a USB keyboard.** The I-brick has no PS/2
  keyboard path; the PROM's attempt to open one fails (observed in the PROM
  run) and it keeps the menu on the serial console with the board drawing
  nothing. The I-brick's keyboard and mouse are USB, on the controller at head
  F slot 5; without a function plugged into the OHCI there is none. With the
  USB keyboard and mouse fitted, `console = g` draws the PROM menu on the
  pipe.
- **X needs an IRIX install with the IP35 graphics subsystems.** With the
  KONA subsystems for the pipe, or the VPro ones for the V12, installed, IRIX
  starts Xsgi and xdm on its own and shows the SGI login on the board. The
  disk must also carry no stale keyboard or mouse bindings in
  `/etc/ioconfig.conf`: IRIX would number the USB devices 1, and X reads
  device 0.
- The status bar's activity bits and processor-clock blink are not wired.
- Everything the [Origin 3200](origin3200-ip35.md#approximations-and-limits)
  lists still applies: one processor per C-brick, no cache coherence between the
  nodes, and a reset of either node resets the machine.
