# The R4600 — expectations and the first real run

The suite selects its expectations by `PRId`. The R4400 and the R5000 have both
run it on real Indys and pass every check (`oracle/`). A real R4600 has now run
it too, though not in an Indy: on a Killer Instinct arcade board (Midway
A-19489; PRId `0x2020`, FIR `0x2020`, Config `0x000264B3`), built little-endian
and launched from that board's boot ROM. Its first run failed 37 checks in 7
tests; with the changes below, the second run passes every check. This file
says where each R4600 answer comes from, so that a failure on an R4600 can be
weighed properly.

The board run is not a log under `oracle/`: the board has no serial port, and
the results were read off its screen. Every byte-order expectation took its
little-endian branch there, so the run confirms the R4600's behaviour, not the
big-endian tables.

## Measured on the KI board

One of the first run's causes was a bug in the test, three were the R4600
differing from both the R4400 and the R5000:

| tests | what was measured | now expected |
|---|---|---|
| `umode/load_miss_third`, `umode/kseg0_load_third` (irix5 only) | **test bug:** the User code logged its address with `sd`, which is a Reserved Instruction in User mode with UX clear, so the load under test never ran and every later record shifted by one. Any MIPS III part does this; the Indy oracles predate `umode/` | the code logs with `sw`, on every CPU |
| `umode/kseg0_load_first`, `umode/kseg0_load_third` (irix5 only) | BadVAddr after a User load from `0xFFFFFFFF80000000` with UX clear reads `0x3FFFFF0080000000`: the low 32 bits are right, the upper ones are not the sign extension. With UX set it is the sign-extended address | that value, on the R4600 with UX clear. Only that one address was measured |
| `fpu/compare_nan`, `fpu/cmp_signalling_qnan`, `fpu/cmp_trap_on_signal` | Invalid only for the signalling predicates (cond 8-15), for a quiet NaN (`0x7FC00000`) as for a signalling one — the manual's pseudocode exactly. So with Invalid enabled, `c.olt` on a quiet NaN does not trap, and stores false | on the R4600 |
| `fpu/vec_cvt_from_l` | `cvt.s.l` / `cvt.d.l` of values past 2^53 convert in hardware, with no Unimplemented Operation trap, to the correctly rounded results and flags already in the table | on the R4600 |

Everything else in the table below passed on the board as it stood.

The reason the case exists at all is the `sgiindy_MiSTer` FPGA core, which
presents itself as an R4600 (PRId/FIR `0x2020`): IRIX 5.3 hard-codes a 32-byte
data-cache line for imp 0x20 and a 16-byte one for the R4400, so that core
cannot pose as an R4400. Before this case existed, `identify()` refused imp 0x20
with rc=127.

## What the suite does not cover on an R4600

Things a real R4600 differs in that no test here looks at, so a pass says
nothing about them:

- **No Watch registers** (WatchLo/WatchHi, the Watch exception), no secondary
  cache (Config.SC = 1) and so no cache-error or VCE exceptions.
- **The cache organisation beyond correctness.** `cache/set_conflict` checks
  that a set conflict never returns the wrong line, not how many ways hold a
  line. A direct-mapped cache that reports R4600 geometry passes — which is
  exactly what the `sgiindy_MiSTer` core has.
- Anything about `Config.EC` / the clock ratio, which the PROM reads per CPU
  family.
